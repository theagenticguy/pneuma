# omnigent-blackboard-poc · Debugging guide

Something is broken. Where do you look first?

This kernel treats failures as values, not thrown surprises. Every mutating command runs inside one transaction; per ADR-0014 the `DomainError` catch lives OUTSIDE the `async with uow.begin()` block, so a raised domain error propagates out of the context manager and the unit of work rolls back naturally (catching inside the block used to let control fall through to a clean `__aexit__` that committed an empty/partial transaction — the latent partial-commit trap this change closed). The catch then translates the error into a structured `CommandResult` with a stable `code` and `status`, and writes one durable row to the append-only `command_failures` ledger in a SECOND, best-effort transaction (`src/sdlc_blackboard/application/use_cases/base.py:53-69`). So the first move in almost every case is: read the `CommandResult.status` / `CommandResult.error.code` the caller got back — it names the failure precisely. As of commit 19fd0da, the ledger is a durable second look: even a caller that dropped the `CommandResult` can now reconstruct what failed for a goal via `blackboard thrash` or a direct `command_failures` query. The exceptions to the value-not-exception rule are raw infrastructure faults (asyncpg, pool, dbmate) that escape the domain catch entirely — these do NOT write a ledger row (the catch is `DomainError`-only) and surface untranslated — plus a small class of DB-constraint violations. Those are what this guide maps.

Two caveats set expectations. First, structlog is wired (`src/sdlc_blackboard/infrastructure/logging.py:24`): each entrypoint calls `configure_logging` from `Settings.log_level` / `log_format`, so you get structured log lines (pretty console in dev, orjson JSON in prod) in addition to the durable surfaces — the append-only `team_events` table, the `outbox` table, the new `command_failures` ledger, and the `CommandResult` envelope itself. The ledger write is best-effort: if that second transaction itself fails, the original command error is still returned unmasked and a `command.failure_unrecorded` warning is logged rather than propagated (`src/sdlc_blackboard/application/use_cases/base.py:88-102`). Second, the MCP server runs with `mask_error_details=True` (`src/sdlc_blackboard/interfaces/mcp/server.py:67`), so an untranslated exception reaches the client as a generic masked error; you must inspect server-side state (the logs, the ledger, and the DB) to see the real cause.

| Symptom | Likely surface | First check | Citation |

| Command returns `stale_version` status; mutation silently did nothing | Optimistic-concurrency CAS lost the race (another writer bumped `version` first) | Re-read the entity's current `version`, confirm it advanced, retry with the new version | `src/sdlc_blackboard/application/use_cases/task_service.py:123-127` |
| Worker mutation returns `stale_assignment`; worker "lost authority" | Fencing-epoch guard rejected a stale claim (task was reclaimed under a newer epoch) | Compare `context.assignment_epoch` against the task's current `assignment_epoch` | `src/sdlc_blackboard/application/use_cases/task_service.py:410-416` |
| Command returns `unauthorized` for a task the actor thought it owned | Actor guard: `assigned_actor_id` does not match the caller | Read the task's `assigned_actor_id`; confirm the caller claimed it and still holds the epoch | `src/sdlc_blackboard/application/use_cases/task_service.py:418-420` |
| `submit_task_result` returns `precondition_failed` (InputManifestMismatch) | Submitted `input_manifest` differs from the run's recorded manifest | Fetch the runtime run and diff `run.input_manifest` against the submitted manifest | `src/sdlc_blackboard/application/use_cases/task_service.py:222-223` |

| `create_task` returns `conflict` on a task_key | A task with that `(goal_id, task_key)` exists with a different contract | Read the existing task; diff its `contract` against the new request | `src/sdlc_blackboard/application/use_cases/task_service.py:64-68` |
| Command returns `conflict` retryable=true, then a retry replays cleanly | Two concurrent calls reused one `command_id`; the losing INSERT hit the dedup unique index | Confirm the retry replays the winner's stored response (safe to retry) | `src/sdlc_blackboard/infrastructure/repositories/idempotency.py:52-59` |
| Double-claim on a task returns a clean `conflict` ("task already has an active assignment") | `open_assignment` INSERT violated the `one_active_assignment_per_task` partial unique index; the adapter now translates the `UniqueViolationError` into a typed domain `Conflict` | Confirm the loser got a `conflict` status; re-read task state and retry a fresh claim | `src/sdlc_blackboard/infrastructure/repositories/tasks.py:224-231`, `migrations/20260717000001_initial.sql:57-59` |
| Any tool errors with a generic masked message, no domain code | A non-`DomainError` exception (raw asyncpg / infra) escaped `_command`'s catch and was masked by `mask_error_details=True` (and left NO `command_failures` ledger row — the catch is `DomainError`-only) | Inspect the DB directly; the domain catch only handles `DomainError`, so infra faults appear opaque and unrecorded in the ledger | `src/sdlc_blackboard/application/use_cases/base.py:66-69`, `src/sdlc_blackboard/interfaces/mcp/server.py:67` |
| `RuntimeError: Postgres pool has not started` | The asyncpg pool was accessed before `start()` or after `stop()` | Verify the DI container lifespan started the pool before any tool ran | `src/sdlc_blackboard/infrastructure/postgres.py:76-79` |
| `RuntimeError: dbmate not found on PATH` during `migrate` | The dbmate binary is not installed | Run `mise install`, or use the `apply_sql_files` asyncpg fallback | `src/sdlc_blackboard/infrastructure/migrations.py:38-39` |
| Commands hang, then fail after ~30s | asyncpg pool `command_timeout` elapsed (default 30s) or the pool is exhausted (`max_size=20`) | Check for a long-held transaction / lock; verify pool sizing under load | `src/sdlc_blackboard/infrastructure/postgres.py:52-68` |
| `command.failure_unrecorded` in the logs; a known failure has no ledger row | The best-effort second transaction that writes `command_failures` itself failed (DB down mid-command, ledger-table drift); the original error was still returned unmasked | Do not trust `blackboard thrash` counts as complete after this warning; grep the logs for the underlying error and reconcile against `team_events` | `src/sdlc_blackboard/application/use_cases/base.py:88-102` |
| Read tool (`get_goal`/`get_task`/`get_artifact`) returns a masked ToolError | The requested id was not found; read side raises fastmcp `ToolError`, which the server masks | Confirm the goal/task/artifact id exists via a goal snapshot | `src/sdlc_blackboard/interfaces/mcp/tools_read.py:25-47` |

## Log and error surfaces

Structured logging is wired via structlog (`src/sdlc_blackboard/infrastructure/logging.py:24`), configured once per entrypoint from `Settings.log_level` / `log_format`. Beyond those log lines, the durable operational signal lives in the database (now including the append-only `command_failures` ledger) and in the structured command envelope. No sentry/datadog bootstrap exists in source.

| Surface | Where it emits | What to grep for | Citation |
|---|---|---|---|
| `CommandResult` envelope | Returned to the MCP caller on every mutating tool | `status`, `error.code`, `error.retryable`, `replayed` | `src/sdlc_blackboard/application/results.py:83-102` |
| `command_failures` ledger | Append-only Postgres table, written in a SECOND best-effort transaction after any `DomainError` | `error_code` filtered by `goal_id` (or `task_id`); one row per failed attempt, never deduped | `migrations/20260721000001_command_failures.sql:12-26`, `src/sdlc_blackboard/infrastructure/repositories/failures.py:22-64` |
| `blackboard thrash GOAL_ID` | Operator CLI stdout; derived report over `command_failures`, reviews, events | `conflicts`, `stale_versions`, `review_rejections`, `reclaims` (orjson JSON) | `src/sdlc_blackboard/interfaces/cli.py:104-122`, `src/sdlc_blackboard/application/use_cases/thrash_service.py:39-63` |
| `team_events` table | Append-only Postgres table, written in the command transaction | `event_type` (e.g. `task.assigned`, `task.submitted`, `artifact.promoted`, `review.invalidated`, `review_task.reopened`) | `migrations/20260717000001_initial.sql:201-218` |

| Structured log line | stdout via structlog (console in dev, orjson JSON in prod) | `command.executed`, `command.failed`, `command.failure_unrecorded`, `command.replayed`, `command.mismatch` | `src/sdlc_blackboard/application/use_cases/base.py:64-102` |
| MCP masked error | Returned to client with details hidden (`mask_error_details=True`) | generic masked message — inspect DB state, not the message text | `src/sdlc_blackboard/interfaces/mcp/server.py:67` |

## First-checks ladder

1. Read the `CommandResult.status` and `CommandResult.error.code` the caller received — nearly every domain failure names itself here before you touch the DB `src/sdlc_blackboard/application/results.py:83-102`.
2. If `error.retryable` is true (only `ConcurrentCommandConflict`), retry the command with the same `command_id`; the winner's stored response replays `src/sdlc_blackboard/domain/errors.py:69-80`.
3. If the caller no longer holds the `CommandResult`, run `blackboard thrash GOAL_ID` (or query `command_failures` by goal) to see which failures accumulated — conflicts and stale versions come straight off the durable ledger `src/sdlc_blackboard/interfaces/cli.py:104-122`.
4. For a `stale_version` or `conflict` (CAS) failure, re-read the entity's current `version` / current alias revision and retry with the fresh value `src/sdlc_blackboard/application/use_cases/task_service.py:123-127`.
5. For a `stale_assignment` or `unauthorized` failure, read the task's `assignment_epoch` and `assigned_actor_id` and confirm the caller still holds the claim `src/sdlc_blackboard/application/use_cases/task_service.py:410-420`.
6. Print the goal's event trace and gate status via the operator CLI to see the ordered history and what the release gate is missing `src/sdlc_blackboard/interfaces/cli.py:71-101`.
7. If the error is generic / masked with no domain code AND no `command_failures` row exists for it, the fault is infrastructure (asyncpg/pool) that escaped the `DomainError`-only catch — inspect the DB directly rather than the masked message `src/sdlc_blackboard/application/use_cases/base.py:66-69`.
8. Query `task_assignments` for `state in ('assigned','running')` to confirm the single-active-assignment invariant held (a double-claim now surfaces as a clean domain `conflict`, translated at the adapter edge) `migrations/20260717000001_initial.sql:57-59`.
9. Inspect the `outbox` for rows where `published_at is null` with rising `attempts` — stuck integration events accumulate here `migrations/20260717000001_initial.sql:229-241`.
10. Verify the Postgres pool started and is not exhausted / timing out (`command_timeout=30s`, `max_size=20`) before suspecting deeper faults, then hit `/health` to confirm the process and DI container came up at all `src/sdlc_blackboard/infrastructure/postgres.py:52-79`, `src/sdlc_blackboard/interfaces/mcp/server.py:71-73`.

## Known incident patterns

No `INCIDENT` / `POSTMORTEM` / `FLAKY` / `KNOWN BUG` tagged comments and no INCIDENTS.md pointer file exist in source (`grep -rni "INCIDENT\|POSTMORTEM\|FLAKY\|KNOWN BUG" src/` returns no matches). The patterns below are the designed-for race conditions the code comments explicitly document as expected concurrency hazards. As of commit 19fd0da these hazards are also countable per goal via `blackboard thrash`, which aggregates them off the `command_failures` ledger, reviews, and events (`src/sdlc_blackboard/application/use_cases/thrash_service.py:39-63`).

- **ConcurrentCommandConflict:** two concurrent calls reuse the same `command_id`, both pass the dedup SELECT, and the second `processed_commands` INSERT loses the race. Signal: `conflict` status with `retryable=true`, and a `conflict` row in the goal's `command_failures` ledger. Mitigation: retry with the same `command_id` — the losing transaction rolls back and the retry replays the winner's stored response. `src/sdlc_blackboard/infrastructure/repositories/idempotency.py:52-59`
- **Double-claim (typed Conflict):** two workers claim the same READY task; the `one_active_assignment_per_task` partial unique index rejects the second `open_assignment` INSERT. The adapter now translates that raw asyncpg `UniqueViolationError` into a typed domain `Conflict` at the adapter edge — symmetric with the dedup path, so no raw 500 leaks. Signal: a clean `conflict` status ("task already has an active assignment"); the failure is recorded with only a `task_id`, and the thrash report resolves it back to the goal via a task->goal join. Mitigation: the DB constraint prevents the double assignment; the loser re-reads task state and retries a fresh claim. `src/sdlc_blackboard/infrastructure/repositories/tasks.py:224-231`, `migrations/20260717000001_initial.sql:57-59`, `src/sdlc_blackboard/infrastructure/repositories/failures.py:49-64`
- **StaleAssignment (fencing epoch):** a worker keeps acting after its task was reclaimed under a newer `assignment_epoch`. Signal: `stale_assignment` status; each reclaim also shows up in the thrash report's `reclaims` counter (derived from `review_task.reopened` events plus per-task `assignment_epoch` above 1). Mitigation: the epoch guard rejects the stale mutation; the worker must re-claim to obtain a current epoch. `src/sdlc_blackboard/application/use_cases/task_service.py:410-416`, `src/sdlc_blackboard/application/use_cases/thrash_service.py:52-55`
- **Stale review/approval on artifact promotion:** promoting an artifact alias to a new revision silently invalidates reviews and revokes approvals bound to the superseded revision, in the same transaction. Signal: the release gate reports `stale_review_ids` / `missing_approvals` after a promotion. Mitigation: re-review and re-approve against the current binding fingerprint. `src/sdlc_blackboard/application/use_cases/artifact_service.py:56-62`, `src/sdlc_blackboard/application/use_cases/gate_service.py:99-114`
